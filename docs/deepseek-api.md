# Spike: подключение DeepSeek и форматы ответов

> **Задача:** подключиться к DeepSeek API и проверить структурированный (JSON)
> вывод для сценариев PoC — генерация задач, вопросы по решениям, профиль,
> roadmap — и обработку ошибок (невалидный JSON, лимиты, таймауты, ретраи).
>
> **Критерий готовности:** стабильный структурированный вывод по каждому
> сценарию и задокументированные ограничения и поведение при ошибках.
> **Зависимости:** нет.

## Что сделано

- Клиент `zero_knowledge.llm.DeepSeekClient` (`src/zero_knowledge/llm/deepseek.py`):
  реализует границу ZEROK-1 `generate(prompt) -> str` и JSON-режим для сценариев.
- Сценарии PoC и раннер: `spikes/deepseek_api/run_check.py`.
- Тесты обработки ошибок на mock-транспорте: `tests/test_deepseek_client.py`.
- В `pyproject.toml` добавлена зависимость `httpx` и `pythonpath = ["src"]`.

## Точка доступа

Команда обращается к модели через LiteLLM-шлюз **`https://llm.azati.ai`**
(OpenAI-совместимый прокси), а не напрямую к `api.deepseek.com`. Доступные
модели: `deepseek-chat` (используется в PoC), `qwen3.8`, `gemma4-12b`.

Ключ — это **virtual key шлюза**, а не сырой ключ DeepSeek: напрямую против
`api.deepseek.com` такой ключ даёт 401, на шлюзе работает.

## Настройка

Ключ в репозиторий не включается. Переменные окружения (см. `.env.example`):

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DEEPSEEK_API_KEY` | — (обязательна) | Virtual key шлюза |
| `DEEPSEEK_BASE_URL` | `https://llm.azati.ai/v1` | Базовый URL (шлюз) |
| `DEEPSEEK_MODEL` | `deepseek-chat` | Модель |
| `DEEPSEEK_TIMEOUT` | `30` | Таймаут запроса, сек |
| `DEEPSEEK_MAX_RETRIES` | `3` | Число повторов при сбоях |
| `DEEPSEEK_MAX_TOKENS` | `4096` | Лимит выходных токенов |


## Сценарии и валидация

Каждый сценарий возвращает один JSON-объект и валидируется Pydantic-схемой
(`extra="forbid"`, перечисления зафиксированы).

| Сценарий | Промпт | Валидация |
|---|---|---|
| генерация задач | `build_task_generation_prompt()` (ZEROK-4) | `parse_and_validate_block` → `Task`/`ReferenceSolution`/`TestCase` |
| вопросы по решениям | `build_questions_prompt()` | spike-схема `SolutionQuestionnaire` (каноническая — TBD) |
| профиль | `build_profile_prompt()` | `KnowledgeProfile` |
| roadmap | `build_roadmap_prompt()` | `Roadmap` |

JSON-схема для модели строится вызовом `Model.model_json_schema()` и передаётся
в промпте — без дублирования списков полей (как в ZEROK-4).

## Поведение при ошибках

Классификация ошибок — два непересекающихся класса:

| Класс | Исключение | Retry? | Примеры |
|---|---|---|---|
| инфраструктура | `ProviderUnavailableError` | по типу | auth, rate limit, 5xx, timeout, сеть |
| контент | `DeepSeekJsonError` / `GeneratedBlockInvalidError` | — | невалидный JSON, нарушение схемы |

Правила retry внутри клиента:

- **401/403** — немедленная ошибка, без повторов (повтор не поможет).
- **429 / 5xx** — повтор с экспоненциальной задержкой (≈0.5s → 8s, джиттер) и
  учётом заголовка `Retry-After`.
- **timeout / сетевая ошибка** — повтор с той же задержкой.
- **прочие 4xx** (например, превышение контекста) — немедленная ошибка; тело
  ответа попадает в сообщение.
- после исчерпания `DEEPSEEK_MAX_RETRIES` — `ProviderUnavailableError`.

Обработка невалидного JSON:

- клиент вырезает JSON-подстроку из ответа, снимая Markdown-ограждения
  (```` ```json ````) и игнорируя хвостовой текст;
- если JSON-объекта нет или корень — не объект, поднимается `DeepSeekJsonError`.

## Результаты (live, шлюз llm.azati.ai, deepseek-chat)

Все четыре сценария дают стабильный структурированный вывод и проходят
строгую Pydantic-валидацию.

| Сценарий | Результат | Время | Валидация |
|---|---|---|---|
| генерация задач | ✅ 3 задачи / 3 эталонных решения / 6 тестов, сложности `easy`→`medium`→`hard` | ~9.8 с | `parse_and_validate_block` |
| вопросы по решениям | ✅ 5 вопросов | ~2.9 с | `SolutionQuestionnaire` |
| профиль | ✅ 4 навыка + 2 заблуждения | ~3.2 с | `KnowledgeProfile` |
| roadmap | ✅ 6 шагов + 3 рекомендации | ~4.8 с | `Roadmap` |

Проверка строгого режима `json_schema`:

- `response_format={"type":"json_object"}` — **работает** (основа сценариев);
- `response_format={"type":"json_schema", ...}` — **не поддерживается**:
  HTTP 400 `This response_format type is unavailable now` (ограничение
  DeepSeek через шлюз).

## Ограничения

- **JSON mode требует слова «json» в промпте.** Все промпты сценариев содержат
  JSON-схему, поэтому требование выполняется; для произвольного промпта это
  ограничение надо учитывать.
- **`json_object` vs `json_schema`.** Работает только
  `response_format={"type": "json_object"}`; строгий `json_schema` недоступен
  (400). Значит, гарантия структуры обеспечивается валидацией Pydantic на
  стороне сервиса, а не режимом strict на стороне модели.
- **Вопросы по решениям** пока используют spike-схему; каноническая схема
  подлежит согласованию (отдельная задача).
- **Глубина контента не проверяется.** Валидация подтверждает структуру и
  согласованность ссылок, но не педагогическое качество (граница гарантий ZEROK-4).
- **Модель может добавлять лишние поля.** Они отклоняются `extra="forbid"` и
  превращаются в `GeneratedBlockInvalidError`/`ValidationError` — это ожидаемо,
  а не сбой инфраструктуры.
- **Детерминизм не гарантируется.** Даже при `temperature=0` возможна
  вариативность; стабильность обеспечивается валидацией схемы, а не
  идентичностью ответов.
- **Шлюз — внешняя точка.** Доступность и лимиты `llm.azati.ai` управляются вне
  проекта; клиент лишь корректно обрабатывает их ошибки.
